# 회의 분석 안정화 및 배포 기록 — 2026-08-03

## 목적과 범위

회의 업로드 분석의 시간 동기화, 화자 분리, 키워드 후보, 처리 시간, 재생 권한 문제를 실제 KTV 브리핑과 클로바 노트 정답 페어를 중심으로 점검했다. 이 문서는 이 주제의 **단일 기준 문서(canonical source)**다. 구현 결과, 비용 원장, 운영 정책, 다음 실행 항목을 이 파일에 통합하며 별도 요약 문서를 중복해서 만들지 않는다.

## 읽는 순서와 상태 기준

1. 아래의 현재 상태표와 다음 실행 백로그에서 지금 해야 할 일을 확인한다.
2. 각 항목의 근거 파일과 검증 명령으로 결과를 재현한다.
3. 운영 배포 전에는 배포 게이트를 모두 통과시키고, 비용 원장과 revision을 함께 기록한다.

상태는 다음 세 가지로만 관리한다.

- **완료**: 로컬 코드와 자동 검증까지 끝남.
- **스테이징 필요**: 로컬 검증은 끝났지만 KMS·GCS·실제 계정·운영 Worker가 필요한 항목.
- **추가 구현**: 정답 데이터나 운영 결정이 없어 아직 코드로 확정하지 않은 항목.

## 03:59 분석 실패의 근본 원인과 해결

2026-08-03 03:59 KST에 시작한 KTV 분석은 04:09 무렵 72%에 있었고, 04:14 UI가 실패를 표시했다. 그러나 저장 기록과 사용량 이벤트를 대조하면 실제 작업은 약 14분 뒤 정상 완료되었고, 두 번째 실행도 정상 완료되었다. 즉 GPU/모델이 72%에서 죽은 것이 아니라 **상태 조회 GET API가 12분 지난 실행 중 회의를 stale로 오판해 error로 변경한 가짜 실패**였다. 뒤에서 계속 돌던 분석이 나중에 `done`으로 다시 덮었다.

적용한 원칙과 변경:

- 상태 조회 GET은 더 이상 회의나 작업 상태를 변경하지 않는다. Worker heartbeat와 명시적 작업 전이만 생명주기의 근거다.
- 로컬 `npm run dev`도 queue + 별도 analysis worker로 실행해 Next `after()` 수명과 HMR에 긴 분석을 맡기지 않는다.
- Node 24/tsx에서 Worker 진입점의 최상위 `await`가 CommonJS 변환 오류로 즉시 종료되고, 그 다음에는 `react-server` 조건 누락으로 `server-only` import가 막히는 문제를 실제 `npm run dev`에서 재현했다. dotenv 뒤 동적 의존성 로드를 `main()`으로 옮기고 단일/풀 Worker 실행 모두에 서버 조건을 적용했다. 로컬 Web과 Worker 2개가 함께 기동되고 SIGINT 종료되는 것까지 확인했다.
- Worker는 30초 heartbeat를 남기고, heartbeat가 3분 끊긴 작업만 최대 3회 지수 backoff로 재시도한다.
- 진행 UI의 모델 기반 “1분 남음” 추정은 제거했다. 대기/활동/확인 중과 실제 경과시간을 표시하고, 10분 이후에도 분석이 계속 진행 중임을 명시한다.
- 준비 단계와 실제 전사 진행률을 분리해 새 분석은 항상 1%에서 시작한다. 기존 0.08 준비값을 3–72% 구간에 선형 반영하던 계산이 9% 점프의 원인이었다.
- 사용자 화면/API 응답에서는 서버·Worker·저장소·KMS 같은 내부 운영 용어를 제거하고, 원인별로 필요한 입력 문제만 남긴다. 로딩은 호흡하는 중심 원과 회전 링, 진행 바를 사용하며 `prefers-reduced-motion`에서는 정지한다.
- 본 전사와 단어 시각의 두 원격 오디오 호출을 청크 안에서 병렬 실행한다. 문맥이 필요한 본 전사 청크 순서는 그대로 유지한다.

4개 실측에서 15분 파일은 59.4초/68.9초, 4분 32초 파일은 18.9초, KTV 11분 44초는 48.6초에 **STT+단어 시각**을 끝냈다. 이는 전체 제품 파이프라인 시간이 아니라 오디오 분석 단계 측정이며, 구조화와 로컬 화자 분리 시간은 별도다. GPU 워커 변경은 이번 장애의 해법이 아니다. 강제정렬을 이미 제거한 뒤 주 병목은 원격 API 두 패스의 직렬 대기였기 때문이다.

- 빠른 모드는 화자분리를 하지 않았는데 요약 모델의 `speakers/timeline` 추정을 참석자 목록에 포함했다. 최종 evidence dialogue에 실제로 붙은 라벨만 참석자 근거로 사용한다.
- 청크별 PRIMARY/TIMED 검수 모델이 TIMED의 앞뒤 3초 문맥을 보고 이미 제거된 경계 단어를 다시 복원했다. 검수 결과를 합칠 때 인접 suffix/prefix 중복을 다시 제거한다.
- 미매칭 단어 보간에서 20~80ms 역전이 생길 수 있었다. 텍스트 offset 순서대로 단조 시각을 강제하고 앞 단어 end를 다음 start에 맞춘다.

`npm run eval:product-transcript-quality`는 유료 호출 없이 가장 최근 빠른/고급 산출물을 찾아 source fidelity, 말풍선 분포, 경계 중복, 참석자 근거, 정답 화자 수, 문장별 요약 근거율, 클릭 시작 오차와 단어 역전을 평가한다. 빠른/고급은 처리 방식이지 화자분리 여부가 아니므로 두 모드 모두 같은 정답 화자 수와 비교한다. 기존 저장 산출물은 자동으로 덮어쓰지 않으므로 현재 보고서는 의도대로 실패하며, 수정 revision에서 재분석한 새 산출물이 통과해야 배포 게이트가 열린다.

## 20251231 재생·화자·말풍선 심층 재현

사용자가 직접 청취해 지목한 03:13, 04:55, 08:13과 `brief-ailab`의 “직접 작동”을 최신 제품 산출물, PRIMARY word timing, 로컬 음향 화자 구간, Clova txt를 같은 절대 시간축으로 대조했다.

### 형광펜 한 단어 지연

`brief-ailab`에서 저장된 시간은 `직접` 32.457–32.897초, `작동하는` 32.897–33.417초였다. 별도 WhisperX 강제정렬도 각각 32.550–32.830초, 32.891–33.371초로 거의 같았다. 따라서 STT timestamp 지연이 아니었다.

실제 원인은 `activeWordFocusAt`이 배열 앞에서부터 현재 발화와 fade를 한 번에 검사한 것이다. 33.0초에는 다음 단어 `작동하는`이 이미 발화 중인데도 앞 단어 `직접`의 0.28초 fade를 먼저 반환했다. 현재 발화 단어를 전체 배열에서 먼저 찾고, 아무 단어도 발화 중이지 않을 때만 가장 최근 fade를 반환하도록 고쳤다. fade 시각 효과는 유지하면서 다음 단어를 가리지 않는다.

### 말풍선/단어 클릭이 직전 답변으로 이동한 원인

최신 KTV 정밀 결과의 손지은 기자 소개 줄은 표시 시작이 488.84초였지만 `words` 배열이 비어 있었다. 실제 Clova 전환은 08:13, 로컬 word timing 복구값은 492.58초부터다. 전역 텍스트 정렬이 일부 교정된 고유명사 때문에 한 줄 전체를 건너뛰자, 앞뒤 글자량 보간값이 직전 답변 끝에 남은 것이 원인이다.

- word timing이 빈 줄만 이웃 말풍선 사이의 좁은 시간창에서 재정렬한다.
- 최소 2개 어휘 앵커와 4글자 이상이 순서대로 일치할 때만 복구한다. 흔한 `네` 하나로는 복구하지 않는다.
- 실제 저장본에 재적용한 손지은 소개는 488.84초/단어 0개에서 **492.58초/단어 6개**로 복구됐다.
- 말풍선 전체 클릭은 줄 시작으로 이동하고, word timing이 있는 각 단어는 해당 단어의 `startSec`로 직접 이동한다. 마스킹 칩 클릭은 원문 보기 동작을 우선한다.
- 정밀 결과에서 본문이 있는데 word timing이 비어 있는 줄이 하나라도 있으면 클릭 게이트를 실패시킨다.

### 말풍선 수와 읽기 단위

기존 KTV 결과는 11분 44초에 82개, 평균 49자였고 40자 미만이 29개였다. PRIMARY 문장을 한 문장당 한 말풍선으로 만든 것이 원인이었다. 같은 화자, 첫 문장부터 25초 이내, 합계 180자 이하를 만족할 때 연속 문장을 묶는다. 저장 원문 글자는 바꾸지 않는다. 기존 KTV 구조를 새 규칙에 적용하면 **82개에서 35개**, 최대 175자, p95 170자가 된다.

### 03:13·04:55·08:13 짧은 화자 경계

단일 cosine threshold 조정으로 해결할 수 없는 세 가지 회의 문법이 동시에 존재했다.

1. 질문자의 “오랫동안 고생 많으셨습니다” → 진행자의 “네, 감사합니다” → 같은 질문자의 질문
2. 진행자의 “네.” → 질문자의 “네, 수석님 ...입니다”
3. 질문자가 곧바로 “네. 수석님 안녕하십니까 ...입니다”

음향 모델은 저음량 인사 구간을 공백 또는 임시 cluster로 만들었고, 의미 모델은 2회의 동일 입력 재현에서도 “네, 감사합니다”를 다음 질문자에게 합쳤다. 비용은 각각 USD 0.005478, USD 0.0055284였다. 텍스트를 바꾸지 않고 위 세 패턴에서 화자 경계만 결정적으로 복구하는 후처리를 추가했다. 이 규칙은 인명이나 언론사를 하드코딩하지 않고 덕담·감사·자기소개·질문 흐름을 사용한다.

Clova txt에서 `참석자 N HH:MM`을 파싱해 17개 turn과 16개 실제 화자 전환을 복구했다. 기존 최신 KTV 빠른 산출물은 정답 8명보다 많은 9명, 정밀 산출물은 8명이었으나 잘못 인식된 이름을 포함했다. 두 결과의 2초 허용 boundary F1은 모두 **0.667**(빠른 precision 0.647/recall 0.688, 정밀 precision 0.714/recall 0.625)로 production 기준에 미달한다. 새 코드 재분석 전에는 개선됐다고 판정하지 않는다. 게이트 기준은 우선 F1 0.90으로 두었다.

단어 시작·끝 MAE는 현재 Clova txt에 단어별 절대 시각이 없으므로 아직 계산하지 않는다. 대신 정밀 결과 word timing coverage 100%, 내부 line-to-first-word p95 0.35초, 역전 0건을 먼저 강제한다. 단어 MAE는 Clova JSON 또는 수동 단어 구간 골드가 확보됐을 때만 활성화한다.

## 저비용 검색 근거 모델 판단

전체 전사문과 마스킹 결과를 검색 모델에 다시 쓰게 하는 것은 채택하지 않는다. 고유명사만 최소 문맥으로 추출해 **원문을 바꾸지 않는 보정 후보**를 만들고, 검색 URL·후보·신뢰도·사용자 확정을 함께 남기는 구조가 적절하다.

- 후보: STT 간 불일치가 있거나 사전에 없고 음향 신뢰도가 낮은 인명·기관명만 보낸다.
- 제외: 일반 문장, 주민번호·전화번호·이메일 등 마스킹 원문, 회의 전체 요약.
- 자동 적용: 사용자/조직 사전에서 이미 확정한 표기만 허용한다. 웹 검색 결과만으로 원문을 자동 덮어쓰지 않는다.
- 권장 실험: Cloud Billing이 연결된 Gemini 2.5 Flash-Lite + Google Search grounding. 2026-08-03 공식 가격은 텍스트 입력 USD 0.10/M, 출력 USD 0.40/M이고 유료 tier 검색 grounding은 일 1,500회까지 추가 요금 없이 제공된다고 안내한다. 다만 가격은 출시 모델에 따라 바뀌므로 배포 시 다시 확인한다.
- 개인정보: 무료 tier는 입력이 제품 개선·사람 검토에 쓰일 수 있어 회의 데이터에 사용하지 않는다. 유료 서비스도 Search grounding 입력/출력을 30일 저장한다고 명시하므로, 최소 고유명사 구절만 보내고 사용자 고지·동의·보존정책을 먼저 마련한다.

현재 프로젝트에는 Gemini 자격증명과 개인정보 동의 흐름이 없으므로 이번 revision에는 외부 호출을 넣지 않았다. 우선 기존 OpenAI 구조화 결과를 원문 불변 후보로 제한하고, 검색 grounding은 별도 feature flag와 비용 원장을 갖춘 뒤 A/B한다.

## 내보내기 가독성과 HWPX 판단

기존 저장 회의도 내보낼 때 같은 화자의 연속 줄을 30초·260자 이내에서 묶고, TXT/DOCX는 `[시각] 화자` 머리글과 본문을 별도 단락으로 출력한다. SRT/VTT cue는 원래의 세밀한 시간 경계를 유지한다. `npm run test:meeting-export`의 한글·마스킹·다중 페이지·모든 포맷 검증을 통과했다.

HWP 바이너리를 직접 만들지 않고 한컴이 공개한 XML 기반 국가표준 HWPX를 쓰는 방향은 맞다. 그러나 현재 Mac에는 한컴오피스/공식 validator/왕복 저장 검증 환경이 없고, 공식 오픈소스 저장소에서도 바로 재사용할 완성 샘플을 확보하지 못했다. 확장자만 HWPX인 불완전 ZIP을 사용자에게 제공하지 않는다. 당장은 한글에서 열 수 있는 DOCX를 유지하고, 실제 한컴에서 열기→수정→다시 저장→재열기 검증이 가능해지면 HWPX를 추가한다.

## 단일 마이크 A/B/C 화자 보존

단독 회의 한 기기 마이크에만 세션 화자 추적을 활성화했다. 팀/초대 회의처럼 참가자별 오디오 트랙이 있는 경로에는 적용하지 않는다.

- 각 VAD 발화의 512차원 화자 임베딩을 추출해 세션 단위 cosine 클러스터 A–H에 누적한다.
- 1.2초 미만 음성은 근거 부족으로 라벨을 강제하지 않는다. 기본 동일 화자 임계값은 0.68이다.
- 원음은 요청 메모리와 임시 파일에서만 사용하고 즉시 삭제한다.
- 개인 세션 centroid는 AES-256-GCM, 팀 세션은 운영 KMS content key로 암호화한다.
- centroid는 재연결 유예 24시간 뒤 maintenance에서 삭제한다. 발화의 `speakerLabel`은 회의 기록 근거로 남는다.
- 실제 KTV 클립 통합 시험에서 같은 진행자는 cosine 0.799로 A/A, 다른 기자는 0.284로 B가 되어 `[A, A, B]`를 유지했다.

요약 모델은 이제 주제·구간만 제안한다. 화면 대화문은 PRIMARY STT 원문을 손실 없이 나눈 evidence dialogue로 다시 만들고, 단어/문장 실측 시각과 음향 화자만 결합한다. 의미 모델이 문장을 의역·생략해도 대화문을 덮어쓸 수 없다. 화자 조정 모델도 블록 범위와 사람 키만 반환하며 텍스트는 원본 블록을 이어 붙인다.

## MP3 → M4A 판단

기존 M4A 변환은 분석 모델 성능이 아니라 브라우저 재생 seek를 위한 것이었다. KTV 11분 44초 MP3를 실제 변환한 결과 3.45MB→2.75MB(20% 감소), 2.1초, `moov/stts/stsz` 표가 파일 앞에 있어 다운로드 직후 정확한 seek가 가능했다. 이 결과로 STT 정확도 향상을 주장할 수는 없다.

- 재생 저장: AAC-LC M4A 16kHz mono 32kbps + faststart 유지
- 정밀 분석 청크: 추가 손실을 피하는 FLAC 유지
- 빠른 분석: 단어용 Whisper를 빼고 저비용 문장 시각 사용
- WAV/OGG/FLAC/WebM/M4A 입력도 재생용 M4A로 정규화하되, 원본 분석과 재생 파생본의 목적을 분리

## 배포 재현성

### 완료, 운영 보정 필요 — 단일 마이크 실시간 A/B/C 화자 식별

참가자별 트랙 회의와 단일 마이크 회의를 분리하고, 단일 마이크에 세션 임베딩/클러스터 저장을 구현했다. 발화마다 모델을 독립 호출해 A/B를 새로 붙이는 구조는 사용하지 않는다.

운영 표본이 쌓이면 다음 값을 재보정한다.

- 배경 잡음·겹침 발화에서 cosine 0.68 임계값
- 1.2초 미만 발화의 미분리 fallback 비율
- A/B/C를 사용자가 실명으로 확정하는 UI
- 최대 8개 초과/동시 발화 시 명시적 `화자 미확인` 표시

### 완료 — 텍스트, 단어 시간, 화자 보정의 단일 진실원천

PRIMARY STT 텍스트를 불변 evidence dialogue로 두고 시간·화자만 결합한다. 구조화 모델 출력의 대화문은 최종 표시 원문으로 쓰지 않는다. 확정 언론사 외 표기 보정은 원문 변경이 아니라 제안으로 남긴다.

### 완료, 스테이징 재검증 필요 — 재생 권한과 대용량 암호화 Range

로컬에서 별도 인증 팀 계정으로 공유 KTV 음성을 열어 11분 44초 duration, readyState 4, 전체 seekable 구간, 재생과 10초 이동을 확인했다. 같은 세션의 HTTP 검증은 전체 `200`/3,613,608B와 `Range: bytes=1048576-1052671`의 `206`/4,096B/정확한 `Content-Range`를 확인했다. 팀 role을 MEMBER로 낮춘 반대 시험은 `403`과 원본 음성 정책 문구를 반환했다. 시험 계정·회의·쿠키 파일은 검증 뒤 정확한 ID로 삭제했다.

신규 팀 원본은 1MiB 독립 AES-256-GCM 청크와 청크별 인증 태그를 쓰는 envelope v2로 저장한다. Range 요청은 겹치는 암호문 청크만 GCS/S3/로컬 저장소에서 읽고, Range 없는 전체 응답도 청크 단위 ReadableStream으로 복호화한다. 따라서 최대 100MiB 파일을 요청할 때 매번 전체 평문 Buffer를 만드는 구조를 제거했다. 기존 envelope v1은 복호화 호환을 유지하므로, 운영의 기존 v1 파일은 별도 rotation 작업 전까지 전체 복호화 fallback을 사용한다. 배포 후 실제 KMS/GCS 환경에서 v2 객체 seek와 v1 rotation을 한 번 더 검증해야 한다.

로컬 100MiB v2 코어 시험에서 중간 4KiB 응답은 암호문 1MiB 청크 하나만 읽었고, Range 복호화는 0.39ms, 해당 구간 전후 RSS 증가는 32KiB였다. 전체 100MiB 암호화는 41.4ms였다. 이는 로컬 crypto 코어 수치이므로 GCS 왕복, KMS data key 조회, Cloud Run 메모리/응답 지연은 스테이징에서 같은 요청으로 별도 측정한다.

`npm run ops:encryption-rotation`은 기본적으로 읽기 전용 inventory만 출력한다. `--execute`를 명시하면 v1 파일을 하나씩 별도 `.v2-rotation` 객체로 쓰고, 전체 평문 SHA-256과 v2 재복호화를 검증한 뒤에만 DB 포인터를 교체한다. 파일별 시도 횟수, 성공/실패, 원본·대상 key, hash, 검증·교체 시각은 `encryption_rotations` 원장에 남긴다. 성공 뒤에도 원본 객체 삭제는 비활성화되어 있으며 별도 승인·보존 정책 전에는 삭제하지 않는다. 로컬 inventory는 팀 암호화 파일 0개였고, 실제 v1 수량은 migration 적용 후 스테이징/운영에서 다시 집계해야 한다.

### 부분 완료 — 배포의 재현성과 관측성

배포 스크립트가 Git `HEAD`를 이미지 태그로 쓰므로 dirty worktree의 실제 소스와 태그가 다를 수 있다. 이번 배포도 이 조건에서 시작됐다. 또한 1초 Cloud Build 폴링은 쿼터 초과를 일으켰다.

- dirty worktree 배포는 이제 명시적으로 거부한다.
- clean worktree의 source revision, image digest, worker revision, migration/verify execution, health 결과를 단일 배포 기록으로 계속 남긴다.
- 10초 이상 저빈도 폴링 또는 Cloud Build event/log 기반 대기
- revision, image digest, worker revision, migration/verify job execution, health 결과를 단일 배포 기록으로 남김

### P2 — 제품 설정과 비용/지연시간 운영 기준

- 계정의 `speakerSplit` 설정은 존재하지만, 업로드 분석의 정책과 명확하게 연결되지 않는다. 표시·동작·fallback을 한 제품 정책으로 정리해야 한다.
